# Контракт как базовая модель вычисления

Статус: проект семантической основы по уточнению владельца от 2026-10-15.
Это направление развития EMS, а не уже реализованная новая грамматика.
Связь: `PROJECT_GOAL.md`, `CONTRACTS.md`, `COMPILER_AND_IR.md`.

## 1. Определение, экземпляр и реализация

Контракт определяет типизированные входы/выходы и операции, допустимые наблюдения,
эффекты, capabilities, ошибки, предусловия и постусловия. Контракт с состоянием
дополнительно определяет начальное состояние, переходы и инварианты.
Версия интерфейса и выбранная реализация фиксируются отдельно.

Экземпляр связывает интерфейс с конкретными состоянием и идентичностью.
Имя переменной ссылается на значение или экземпляр; оно не создаёт новый вид
контракта для каждого написания имени. Неизменяемое связывание значения не требует
выделения изменяемой ячейки. Локальная ячейка и состояние долгоживущего компонента
имеют разные времена жизни и разные правила доступа.

Атомарность в редакторе означает отсутствие раскрываемой EMS-композиции и не
означает транзакционность. Транзакция — отдельное семантическое свойство перехода.
Составная реализация раскрывается в тот же граф; скомпилированная атомарная должна
сохранять наблюдаемое поведение, включая эффекты и ошибки.

## 2. Минимальное ядро: семейства контрактов и правила композиции

Это минимальная практически достаточная основа, не доказательство математически
единственного или наименьшего базиса. Имена ниже обозначают роли, не выпущенные API.

| Основа | Интерфейс и смысл | Что выводится |
|---|---|---|
| Значение | Создать/передать неизменяемое значение T; конструкторы и разбор типизированных вариантов | Литералы, записи, пары, Option/Result |
| Преобразование | `(A, B, …) -> T` с явно заданными ошибками и эффектами | Арифметика, сравнения, преобразования строк |
| Хранение | Создать локальную `Cell<T>`, читать/писать T по разрешённой ссылке | Изменяемая переменная, состояние компонента |
| Композиция | Соединить совместимые порты; передать управление с сохранением порядка эффектов | Программа, повторно используемая операция, последовательность |
| Выбор | По Boolean активировать ровно одну ветвь; разбор варианта по тегу | if/else, match, условное выражение |
| Повторение | Структурная итерация или рекурсивный вызов с областью locals и лимитами исполнения | while, for, fold/map/filter, break/continue |
| Переход | Выполнить композицию над снимком состояния, проверить и подтвердить изменения | Действие компонента, транзакция, откат |
| Событие | Типизированная постановка события и реакция по определённому порядку | Взаимодействие компонентов, реактивное обновление |

Типы, области видимости, правила соединения портов, порядок управления и
транзакций — правила языка. Чтобы выразить их контрактами, исполнителю всё равно
нужны определённые примитивы исполнения. Нельзя считать обычную eager-функцию
`select(a,b)` реализацией ветвления: невыбранная ветвь не вычисляется и не даёт эффектов.
Нельзя реализовать цикл обычным циклом ссылок в finite dataflow IR: его validator
должен продолжать отклонять такой граф. Повторение требует структурной операции IR.

## 3. Пример арифметики

Для неизменяемых `x = 10`, `y = 20`, `z = x + y`:

```
Value<Number>(10) ──x──┐
                      ├── Add<Number> ──z──> result
Value<Number>(20) ──y──┘
```

Для изменяемого x: `Cell<T>.read -> Add<T> -> Cell<T>.write`; ребро управления
обязывает выполнить read до write. Подмена его независимыми dataflow рёбрами
недопустима. Повторное чтение изменённой ячейки не может использовать memo чистого
узла. Константная свёртка и удаление неиспользованного хранения допустимы лишь
при сохранении наблюдений, ошибок и эффектов. Граф должен уметь показывать эти
контракты и сворачивать выражение в удобный составной блок.

В текущем профиле арифметика работает с конечным binary64 `Number`.
`Int` не является его псевдонимом: ширина/переполнение или произвольная точность
требуют отдельного решения, сериализации и одинаковых test vectors всех targets.

## 4. Переходы и инварианты: предлагаемый первый профиль

1. Создание экземпляра проверяет типы начального состояния и инварианты.
2. Входящее событие выбирает переход, создаётся транзакционный снимок.
3. Выполняются предусловия и тело; чтения видят собственные записи транзакции.
4. Проверяются постусловия и все инварианты изменённых экземпляров на финальном
   кандидатном состоянии. Не проверяем инвариант между внутренними присваиваниями.
5. Успех атомарно подтверждает состояние и очередь исходящих событий; ошибка,
   отмена, превышение лимита или нарушение инварианта откатывает оба.
6. UI наблюдает только подтверждённое состояние; реактивные зависимости
   пересчитываются после commit. События идут после commit в определённом FIFO.

Инварианты чистые, тотальные в пределах бюджета, без IO/записи состояния и без
скрытых привилегий. Для нескольких экземпляров нужна общая транзакционная граница;
пока она не реализована, связывание не должно обещать атомарный distributed commit.
Нативные IO-эффекты не откатываются обычным rollback памяти: первый профиль
запрещает их внутри откатываемого перехода. Будущие after-commit операции и
компенсации требуют явного контракта доставки/ошибок.

Для `Counter.value >= 0`: Decrement из 1 подтверждает 0; из 0 даёт
`InvariantViolation`, сохраняет 0 и не посылает событие успешного изменения.
Конкретный код ошибки и представление diagnostics утверждаются с реализацией.

## 5. Обозначения и UI

| Предложение | Семантическое назначение | Что ещё определить |
|---|---|---|
| `@Name` | Определение/использование контракта | Как различаются declaration, instance и operation |
| `::` | Доступ к операции контракта | Версия, namespace, выбор экземпляра |
| `+Transition` | Объявление действия/перехода | Грамматическое отличие от арифметического `+` |
| `? predicate` | Проверяемое ограничение | Инвариант, pre или post задаются явно контекстом |
| `~>` | Связь событий с переходами | Payload, FIFO, backpressure, cancel, ошибки |
| `=>` | Передача типизированного значения | Направление, fan-out, ownership, порядок |
| `<=` | Реактивная зависимость | Отличие от сравнения, циклы, время наблюдения |

Таблица не утверждает грамматику. `@Main` не должен вызывать произвольный host-код:
внешний язык разрешён в реализации контракта, прикладная композиция остаётся EMS.
`UI.Button`, `UI.Window` — семантические интерфейсы; target выбирает реализацию по
capabilities и lock. Поддержка Web не доказывает наличие Windows/Android/iOS backend.
Цикл реактивных зависимостей требует отдельной семантики fixed point или отказа;
первый профиль отклоняет его, а не запускает бесконечную перерисовку.

## 6. Соответствие действующему проекту

| Часть | Уже есть | Не выдавать за реализованное |
|---|---|---|
| Типизированные операции и композиция | Registry, IDL, IR1/IR2, pure compiler, sealed packages | Универсальный переход к новому синтаксису |
| Значения/ветвление/повторение | frontend/control IR, interpreter/compiler, algebraic types | Все операции как редактируемые визуальные порты |
| Хранение и транзакции | локальные locals, state bindings, ReactorKernel FIFO/rollback | Контрактные декларации Cell и Counter с инвариантами |
| UI и события | UIKernel, DOM adapter, typed handlers, самостоятельный Web export | Новый `@Application` frontend и нативные backend |
| Граф и код | Общая компиляция и структурная проекция на основном холсте AC-100 | Полный визуальный редактор всей грамматики |

Существующие `fn`, `let` и compiler intrinsics остаются проверяемым прототипом
семантики. Следующий язык должен опускаться в тот же versioned IR или явно
мигрируемое расширение; отдельный исполнителем «нового синтаксиса» запрещён.

## 7. Следующие проверяемые срезы

1. Семантический lowering простого контракта `@Main` и чистых операций в существующий
   IR; документированная грамматика, graph/text/compiled differential fixture 30,
   type mismatch, unknown operation и duplicate binding отвергаются до исполнения.
2. `Cell<T>`: instance/lifetime/read/write и последовательность; алиасы и scopes,
   отсутствие неверной memoization; сравнение interpreter/standalone.
3. Переходы с инвариантами: Counter traces 1→0, отказ 0→-1, rollback/cancel/limit;
   ни состояние, ни событие успеха не наблюдаются при отказе. Текст и визуальный
   граф создают один проверяемый IR. Поддельные state bindings отклоняются.
4. Семантические UI контракты и event/reactive bindings поверх существующих kernels;
   один counter Web/standalone, позднее отдельные реальные native targets.

До завершения этих gates новый синтаксис и инварианты считаются проектом.

Уточнение интерфейса владельца: отдельные виды узлов для «простого числа», константы или нового элемента не вводятся. В Studio значение задаётся обычному типизированному входу контракта через общий редактор аргументов; подключение другого контракта заменяет это значение связью. Для структурных операций сохраняется задача полной контрактной семантики и общего IR, без отдельной сущности «алгоритм».
