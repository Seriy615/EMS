# Текстовое тело контрактного графа EMS

AC-132, EMS-038; G-01/02/03/04/05/06/11/12/14. Контракт остаётся единственной
единицей композиции. `graph` — форма его тела, а не новая сущность «алгоритм».
Общий parser создаёт `ContractDeclaration.body = ContractGraph`; native-переход
`+Change` также может иметь это тело. Контракт с обычным текстовым блоком
сохраняет прежнюю грамматику и семантику.

```ems
@Main(b: Number, a: Number) -> Number graph {
    @core::sub["1.0.0"] #difference {
        a <= input::b;
        b <= input::a;
    }
    @std::program::Result #result {
        value <= #difference;
    }
    + #difference;
    #difference.next ~> #result.enter;
}
```

Это именно существующий `ems-contract-flow`: `#difference` — стабильный ID узла,
`input::b` — вход контракта, `<= #difference` — связь значения, `~>` — связь
активации, `+ #difference` — единственная начальная активация данного тела.
Порядок узлов и текстовых строк не становится порядком исполнения. `:` задаёт
закрытую константу; вычисляемое выражение необходимо представить контрактом.
По умолчанию версия вызываемого контракта `1.0.0`; квадратные скобки явно её
фиксируют. Печать всегда сохраняет pin, в том числе для registry-контрактов.

Условия представлены `@std::control::If` с входом `condition: Boolean` и выходами
активации `yes`/`no`. Числа сравнивает отдельный контракт. Начало/конец итерации
не передают значения; `next`/`repeat` соединяются с входом `enter` любого узла.
Переменная — тот же контракт с входом записи `value` и выходом текущего значения:

```ems
@std::storage::Variable #count: Number = 0 {
    value <= #increment;
}
@std::storage::Variable #writeAgain: Number = #count {
    value: 7;
}
```

Вторая запись обращается к той же ячейке; собственное начальное значение имеет
только владелец. Остальные виды узлов не объявляют storage. Нечисловые массивы,
Option/Result и Map используют прежние конечные типы; константы имеют формы
`["a", "б"]`, `None()`, `Some(#-0)`, `Ok([true])`, `Map([["key", 2]])`.
В этой позиции конструкторы обозначают данные, не исполняемые вызовы. Обычные
вызовы, арифметика и обращения к состоянию в константах запрещены. Строки `"+"`,
`"-"`, `"!"`, `"await"` остаются строками. Quoted имена поддерживаются; их семантические
имена должны проходить прежние ограничения ID и портов графа.

После `graph` допустима явная строка версии семантического графа, например
`graph "ems-contract-flow/1" { ... }`. По умолчанию `/3`; печать сохраняет исходную
версию `/1`, `/2` или `/3`. Это версия семантики, а не расположения карточек.
Пределы прежние: до 256 узлов в теле, до 33 графовых тел/1024 узлов в модуле,
до 100 входов, конечные значения и стандартные ограничения исходного текста.

## Общая проверка и исполнение

После сбора настоящих интерфейсов и type aliases frontend проверяет граф тем же
`validateContractFlow`: типы, pins, ссылки, data cycles, storage, единственность
активационных выходов и доминирование производителей. Значение не вычисляется
по требованию и не подставляется автоматически при `UNINITIALIZED_FLOW_VALUE`.
Затем общее правило lowering (`src/contracts/flow-source.mjs`) переводит тело
в обычный located AST. Прежние expression/effect checker и control IR2 проверяют
все настоящие тела функций и их транзитивные effects/capabilities. Порядок
параметров текстового интерфейса и вычисления аргументов сохраняется.

Сигнатуры source-контрактов служат только forward references при проверке
портов. Они не регистрируются как atomic/composite реализации, не содержат
`execute` и не передаются runtime. Подмена `sourceSignatures` через options
обычного graph compiler запрещена. Требование `pure` не может скрыть state
операцию в обычном helper. Прямые registry-вызовы сохраняют прежние ограничения
pure/genuine state bindings; права исполнения проверяет прежний runtime.

Смешанные графовые и обычные текстовые реализации, рекурсия, type aliases и
явно предоставленные namespaces доступны в общем frontend. Входы/выходы вызовов
графа должны иметь конкретные конечные типы; generic/async/extern source helpers
не связываются как графовые узлы этого профиля. Native-переходы могут использовать
`@self::value::read/write`, другие операции экземпляра и чистые графовые
initializers/invariants; их связывает прежний native linker. Все экземпляры,
внешние invariant boundaries, общий budget и rollback остаются в Kernel.

Пример: `examples/graph-body.ems`.

```sh
node tools/ems.mjs module-run examples/graph-body.ems --entry demo.CounterFlow '{"limit":3}'
node tools/ems.mjs module-build examples/graph-body.ems --entry demo.CounterFlow --out /tmp/counter.mjs
```

Свежий Node-процесс может импортировать полученный файл и вызвать `execute` без
EMS IDE/сервиса. Это доказательство JS target, не native-компиляторов всех ОС.

## Тот же документ в Studio

«Файл → Код EMS» обычного графа показывает исходные узлы и соединения всех
принадлежащих ему контрактов. Текст можно редактировать, применить к тому же
холсту или скачать как `workflow.ems`. Apply проверяет полную кандидатную
программу; ошибка не меняет сохранённый граф. Незавершённый/ошибочный текст
сохраняется отдельно и восстанавливается после перезагрузки, в том числе offline.
Прежнее визуальное редактирование незавершённых графов, удаление узлов, undo и
черновики продолжают работать; текст не принуждает исполнение такого графа.

Apply сохраняет ID существующих узлов и контрактов, позиции, viewport, описания
и совместимые значения входов. Новые узлы получают только собственные начальные
позиции; существующие не переставляются. Изменение ID в тексте означает новый
узел, а ссылки должны быть обновлены явно. Новый тип входа получает корректное
начальное значение; недопустимое старое значение не приводится неявно.
Удалённые явно в тексте контракты/узлы удаляются вместе с их metadata, никакие
связи не изобретаются. Root ID документа сохраняется.

CAS текстового черновика проверяет его владельца и снимок семантических графов.
Перемещение карточек, pan/zoom, описания и данные запуска не делают текст устаревшим:
текст их не заменяет. Изменение графа требует явной загрузки актуального текста,
предыдущая сохранённая копия остаётся в `.previous`. При quota failure текущий
текст остаётся в памяти и доступен для скачивания. Черновики разных файлов
workspace и разных native/UI scopes не пересекаются. Внешний CAS документа
по-прежнему защищает запись через другое окно.

Чистый `.ems` из графовых тел импортируется как обычный flow-документ с теми же
семантическими узлами/рёбрами; первый графовый контракт является root файла.
Позиции не входят в код: новая копия получает начальные позиции, исходный
документ сохраняет свои. Type aliases разрешены. Смешанные structured тела,
packages/imports нельзя молча потерять при таком импорте — canvas профиль их
отклоняет, хотя общий frontend может их компилировать.

В native/UI graph scope Apply сначала меняет обычный черновик графа. Явное
сохранение модуля/UI проходит прежнюю проверку всего приложения с guards,
полями, событиями и соседними файлами. Код тела, скачанный из такого scope,
требует объявленных родительским модулем state bindings; это не экспорт всей UI
программы. Для независимого приложения используется существующая сборка всего
модуля/UI. Native full-module current source AC-130 продолжает поддерживаться.

Этот срез не завершает полный inverse произвольного EMS. Структура native
definitions/instances/fields/UI не редактируется этим окном; применение их полного
current source поверх исходного документа ещё впереди. При исходном импорте
native-текста с graph-переходом semantic IR сохраняет его поведение, но начальная
визуальная проекция native-модуля пока не сохраняет все авторские ID этого
текстового тела. Архивный текст не подменяет текущую программу; сохранённый
bodyGraph после применения кода в обычном canvas сохраняет ID и layout.
