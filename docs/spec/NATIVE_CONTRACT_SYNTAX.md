# Контрактная текстовая форма — исполняемый профиль 0.1

Задача EMS-038, первый срез AC-102. Это проверяемое начало собственного синтаксиса,
не окончательная грамматика событий, состояний, UI и инвариантов.

```ems
@Numbers::Double(value: Number) -> Number requires pure {
    return core::mul(value, 2)
}

@Main() -> Number requires pure {
    let x = 10
    let y = 20
    return Numbers::Double(core::add(x, y))
}
```

`@` объявляет контракт. `::` выбирает квалифицированное имя или операцию.
Параметры и тип результата пока обязательны. Версия и требования эффекта/прав
используют существующие package/requirements и привязки Registry. Число —
конечный binary64 `Number`; `Int` не вводится как неявный псевдоним.

```ebnf
contract = ["export"], ["extern"], ["async"], "@", qualifiedName,
           [typeParameters], "(", [typedParameters], ")", "->", type,
           [requirements], (block | ";");
qualifiedName = identifier, {("::" | "."), identifier};
```

Для extern требуется `;`, для реализации — body. `::` в вызове формирует тот же
типизированный member access, что существующая квалификация. Это не динамический
вызов host объекта и не обход capability checks. Неизвестная операция и неверные
типы отвергаются обычным checker до исполнения. Пакетная версия по-прежнему
записывается через `package name @ "version"` и не смешивается с объявлением.

Парсер строит существующий `ContractDeclaration` в `ems-ast/1`, затем используются
тот же checker и versioned IR. Нет нового executor или особого типа узла холста.
Имена `Numbers::Double` нормализуются в canonical ID `Numbers.Double`;
полные source locations сохраняют исходный текст с `@`/`::`, включая диагностику
и визуальное редактирование. Строки/комментарии не переписываются.

Обычный finite граф экспортируется в `@`-форму и вызовы `::`; обратное применение
сохраняет сериализованный проект. Структурный контракт с if/for отображается
на основном холсте, редактируется и исполняется через общий IR2.
Существующие `contract`, `fn` и `.` принимаются для совместимости; коллекционные
и UI-генераторы ещё могут выдавать прежнюю нотацию.

Запуск примера:

```
node tools/ems.mjs module-run examples/native-contracts.ems --entry Main '{}'
node tools/ems.mjs module-build examples/native-contracts.ems --entry Main --out /tmp/ems-native.mjs
```

Результат примера60. Отдельный canonical fixture10+20 даёт30 через call IR,
control IR, интерпретатор, compiled module и восстановленный визуальный проект.
Скомпилированный пример проверяется новым Node-процессом вне рабочего каталога EMS.

## Ограничения и следующие срезы

`@Main { ... }` с неявной сигнатурой пока отклоняется: результат и параметры
должны быть явно типизированы. `+Transition`, `? invariant`, `#instance`, `~>` и
реактивные `<=` здесь не реализуются. `<=` сохраняет смысл сравнения, `=>` —
существующий контекст pattern arms; никакой новой семантики молча не добавляется.

Это развитие текстовой формы существующей контрактной семантики, а не завершение
всего контрактного ядра. Следующие части EMS-038: явная семантика Cell/instance,
переходы с транзакционными инвариантами и событиями, затем UI notation. Правила и
критерии — `docs/architecture/CONTRACT_KERNEL.md`. Новые возможности должны
сохранять interpreter/compiled parity и отображаться в том же графе.

AC-102 также устраняет обнаруженную browser regression: сохранение первого
текстового/структурного проекта теперь сохраняет его owner project перед draft.
Иначе после закрытия страницы создавался новый ID и черновик терял привязку.
